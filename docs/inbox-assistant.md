# 会话助理

排队或分析中的事项可在工作台详情或飞书待办卡片点击「停止深度分析」。这会中止该事项的分析和限流重试，保留待办、已有草稿及话题，不会把它标记为已处理，也不会影响其他会话或轻量筛选。同一事项的新消息、Bridge 重启不会自动恢复已停止的深度分析；需要时点击「深入分析」或「分析 / 重试」重新启动。停止操作按事项版本校验，旧页面的操作不会取消新一轮分析。托管工作台仅在已连接的 Bridge 支持停止操作时展示按钮。

支持统一配置的新版可通过 `monitors init` 把飞书与 CI 设置迁移到同一个 [monitors.toml](monitor-config.md)。工作台设置继续可用，并回写该文件。

操作入门见[用户手册](user-guide/assistant.md)。GitLab CI 现通过公共任务来源入口进入助理，复用事项生命周期、分析队列、结果与草稿、复核和通知机制。本地工作台统一展示并可按来源筛选；盯盘保持独立开关，不经过个人关注筛选。下文的采集、范围及开关规则指飞书消息来源，关闭它不会关闭独立开启的盯盘。来源和迁移细节见[盯盘用户文档](user-guide/monitoring.md)。

助理随 Bridge supervisor 启动，复用个人 Claude 或 Codex 执行 profile 的用户授权。托管工作台连接在助理关闭时仍保持心跳，可查看历史、编辑草稿和标记处理。

## 工作流

采集入口按当前执行 profile 的应用 ID 和 bot open_id 直接排除助理自身发言，不创建筛选事项。历史纯自身事项启动时转为忽略并取消重试；混合事项只移除助理消息，保留真人和其他机器人内容，必要时重新筛选。手动选会话和深入分析的上下文读取也执行同样过滤。自身身份来自已连接 profile，不按显示名称或消息内容推断。

加载身份校验版本后，采集、聊天回查、筛选及深入分析材料保留结构化 @ 对象的姓名和 ID，并按 `ownerOpenId` 计算是否为本人。正文或转发中的 `@姓名`、`<at>` 文本不能充当结构化 @ 证据。群聊的 `needed/uncertain` 筛选结果须提供 `ownerMentionMessageIds`：引用的消息必须在输入或聊天快捷工具回查结果中确实 @ 了本人，否则进入现有结果纠正/重试流程。没有 @ 证据时填空数组，仍可凭明确职责、交办或系统影响判断相关性；此校验不替代对职责和剩余动作的判断。深入分析也需复核筛选归属，不将筛选理由当作已核实事实。仅修改 `attentionProfile` 不会启用这些代码行为，旧运行实例仍需升级并重启。

筛选和深入分析请求均不设置 `max_output_tokens` 或 `max_tokens`，输出长度由模型服务决定。流式响应不按累计流量截断，仍限制单条事件大小，并保留取消和超时机制；服务端标记 `incomplete` 的结果不会作为成功接受。

模型生成的工具参数（含 `argumentsJson`）、最终筛选 JSON 和深入分析结果在严格解析失败后使用 `jsonrepair` 修复语法，再执行字段、类型、事项 ID 与操作白名单检查。修复不增加权限或执行新工具；无法修复或不符合参数 schema 时不执行该调用，在同次筛选中反馈给模型，最多纠正两轮。最终结果仅省略 `priority` 时默认 `normal`，其他必需字段与事项 ID 匹配仍严格验证。配置、凭证、外部 API 响应和 GUI 命令不使用容错解析。

- **关闭**：停止采集、筛选和深入分析，取消排队及正在执行的模型任务。
- **开启**：按接收范围采集消息，合并连续消息后用配置的模型判断是否需要本人关注。新版 Bridge 收到新的 `needed` 判断后直接入队；`pending`、`quiet`、`uncertain` 不自动处理，没有倒计时。已有历史 `needed` 不在升级时批量重跑，用户编辑过的草稿保留人工控制。
- **自动分析与草稿**：轮到事项执行时，先以机器人身份发送“已开始分析”。`deliveryMode=new_topic` 为每项新建话题并保存服务器返回的消息及话题 ID；通知确认成功后才启动配置模型的 agent。结果和回复草稿回复到该事项话题，开启工作台时同样发送。`thread` 模式沿用配置的话题。手动 `process` / `manual` 也使用这一流程；同一事项重试复用已保存的话题。

处理 agent 使用 `analysisModel`，留空时继承执行 profile / CLI 的模型设置。旧 Codex 配置省略此字段时继续使用 `deepseek-flash` 和 `max`；Claude 省略或留空时继承自身默认模型与强度。两端都使用与普通会话相同的运行适配器，继承执行 profile 的环境、权限、MCP、skills 和共享规则配置。任务要求按问题核对相关会话、文档、源码、日志或指标，验证关键假设，标明证据来源与时间，区分事实、推断和缺失信息；本地修改需做针对性验证。agent 在独立的事项工作目录中运行，每项默认最长 30 分钟（支持超时配置的版本可调整，见下文）。允许调查分析和可回滚的本地准备，任务指令要求外部发信、push、合并、部署和生产变更留待用户确认；这属于 agent 任务约束，不是与 profile 权限分离的安全沙箱。agent 只返回结构化结果，发信由 Bridge 负责。仅最终答案进入草稿。执行 profile 开启过程消息时，Bridge 在该事项话题内创建进度气泡，展示公开进度、工具摘要和重试状态；原始推理仅映射为“正在分析和核对信息”，工具参数及原始输出不透传。气泡使用经验证的话题内回复作为锚点，接口失败不阻止分析及最终结果投递。加载支持逐事项筛选的版本后，默认最多同时筛选 50 个事项、深入分析 5 个事项。两类使用同一套调度实现和独立名额，互不占用；每项完成后立即补位。同一事项不会重复并行，停止某一项不会取消其他事项；旧版本仍为单项分析。完成草稿不等于本人已处理。关闭、接手、忽略、范围变更或人工编辑会取消受影响的旧任务，晚到结果不覆盖人工操作。加载增量分析版本后，普通新消息不会取消运行中的分析，按下文增量流程处理。重启中断的 agent 标记失败，保留话题和工作目录，由用户手动重试；已完成待发送的结果可继续投递。

支持逐事项筛选的版本可在监控文件 `[concurrency]` 中配置 `triage = 50` 和 `analysis = 5`，或在工作台“后台任务并发”中调整；两者均为 1–100 的整数，单位都是同时执行的事项数。每个筛选任务只接收一个事项并返回一个判断，单独查询上下文、重试和取消，不再组批。飞书、GitLab CI 和存储告警共用深入分析名额；筛选使用独立名额，因此分析满载不阻塞筛选。每个池按入队顺序执行，一项结束后补位，筛选通过的事项立即进入分析队列，不必等待其他筛选结束。同一会话/话题的连续消息仍合并为一个事项。调高后增加并发；调低时已有任务继续完成，再按新上限补位，不重建服务或中断任务。旧版本保持原有语义，升级后再添加新字段。

加载分析限流恢复版本后，深入分析复用普通对话的 429 重试：按 30 秒、60 秒、120 秒退避，连续无进展最多重试 3 次；恢复有效输出后重置重试次数。有进展时沿用 agent 返回的会话继续，未获得可恢复的会话 ID 时不重跑已执行的工作。等待和重试均计入每项分析总时限，默认 30 分钟；支持超时配置的版本可通过 `analysisTimeoutMinutes` 调整，取消会立即停止等待。额度或授权错误不自动重试。失败事项和话题结果显示脱敏的限流、额度、授权、超时或结果格式原因，原始运行错误保留在脱敏日志中；重试前清除失败尝试的最终文本。旧实例须重启后才具备这些行为。

自身消息硬过滤使用运行时可信的机器人 app ID 和 open ID，同时识别飞书 `sender.id` 与 `sender.open_bot_id`，不依赖模型判断或消息正文。当前结果群及已有事项记录的结果群不作为来源；采集、手动选会话、上下文补充、队列执行和投递均受此约束。启动时把旧的自身消息事项归为忽略并清除筛选/分析/投递重试；混有真实请求的记录移除自身内容后重新筛选，已有草稿标记过期。此类自身事项不可通过恢复或手动处理重新入队；其他机器人的告警仍按个人关联规则筛选。

轻量筛选使用 `triageService` 选择根配置中的独立 Responses 模型服务，不依赖 Codex profile。默认模型和凭据引用在“模型 API 服务”中配置，`triageModel` 非空时只覆盖筛选模型；省略或为空均使用服务默认值，与深入分析的 `analysisModel` 无关。显式服务不存在或凭据无效时直接报错，不回退到其他配置。详见[独立模型服务](model-services.md)。

没有 `triageService` 的旧配置仍使用 `triageProfile` 的 Codex Responses 配置；省略 `triageProfile` 时沿用执行 profile，省略 `triageModel` 时同源筛选沿用 `analysisModel`、跨 profile 使用 Flash，显式留空时使用筛选 profile 的默认模型。升级不会自动复制凭据或改变旧模型策略。筛选直接运行受限工具循环，不启动 Agent，也不加载工作目录、MCP、skills 或共享 agent 指令。飞书读取始终使用执行 profile 的用户授权。模型可调用 `search_messages`、`read_chat_messages`、`read_thread_messages`、`get_messages` 四个聊天快捷工具，以及 `list_lark_read_tools` / `describe_lark_read_tool` / `call_lark_read_tool` 查询已审核的飞书只读目录。目录来自 lark-cli 1.0.77 的 risk=read、支持用户身份的业务接口，覆盖文档、表格、多维表格、日历、任务、邮件、知识库等；仅在用户已有授权内读取，不自动申请或切换权限。程序在执行前校验工具名及参数，固定以当前 bridge-bound 用户身份调用固定白名单中的读取命令；无 shell、文件读写、任意 CLI/API、附件下载、发消息或其他 agent 入口。每个目录操作固定命令路径和允许参数；禁止 `@file` / stdin、输出路径和全局参数覆盖，路径标识符拒绝遍历和 URL 注入。目录排除下载、导出任务、本地 Git 凭证、API key、生成分享链接、监听落盘及本地目录比对。纪要只查摘要等内联信息，画板仅返回原始结构，表格单次输出限制 20,000 字符。查询返回值有长度上限及截断/分页提示。新增接口或升级 CLI 时需重新审核目录，不能凭命令名猜测只读。查询失败进入自动重试，发通知仍由外层服务统一处理。

逐事项筛选版本每次只筛选一个事项。支持摘录配置的版本默认每项最多 12 条、每条 2000 字符（旧版固定为 6 条、500 字符），由 `triageMessageLimit`（2–100）和 `triageMessageChars`（200–16000）控制。保留最早留存消息及近期实质内容，长消息保留首尾并标明截断；已识别的 bot 进度、空内容状态不占条数。关注背景最多 3000 字符；工具可补充相关飞书资料，不能把摘录缺失当成没有交办或剩余问题的证据。输入聊天不能作为系统指令。最终判断为单个 JSON 对象，ID 必须与输入事项一致。筛选和深入分析可并行运行，每次筛选最长 10 分钟，最多 16 轮模型请求（含纠正）、64 次只读工具调用；重复工具调用 ID、未授权工具及超限结果均拒绝。`dailyTriageLimit` 默认每天 1,000,000 次逐事项筛选尝试（含重试；已有当天计数继续累计，新版本每筛选一个事项加一）；一次运行可有多轮模型与工具调用，不等于 provider 的请求数。额度在启动运行前持久化，不限制手动深入分析。

加载解析容错版本后，最终结果、工具参数和目录工具内嵌的 `argumentsJson` 先用严格 JSON 解析，再尝试 jsonrepair 修复引号、尾逗号等语法；未闭合容器/字符串、缺失参数值不自动补全。修复结果仍需通过字段、ID、参数范围与只读白名单校验。仅缺少 `priority` 时默认 `normal`，不猜测 state、reason 或事项 ID。仍无效的工具参数以脱敏 `invalid_arguments` 返回模型，最多纠正两轮，不执行无效调用。

逐事项筛选版本的结果 ID 不匹配、字段无效或本人 @ 证据校验失败时，在当前事项的查询上下文内请求补正，最多两轮；此阶段禁用工具，不重复查询。纠正耗尽或连接中断时，该事项进入自动重试，不影响其他事项。普通只读查询失败会返回模型，要求依赖该查询的事项为 retry；身份不匹配、bridge 未绑定及取消仍中断该次执行。旧批次版本仍使用原有逐项结果保留机制，须重启加载新版本后才使用独立请求。

执行失败、结果缺失/无效及模型报告必要查询未完成时保持 pending，按 30 秒、2 分钟、5 分钟、之后每 15 分钟自动重试；不转人工、不发群。`attention.retry` 持久化 attempts、nextAt 和脱敏错误类别，重启后继续，成功后清除；新消息不会绕过已有失败退避。关闭/范围切换会取消当前子进程，已处理或输入变化后不接收旧失败/结果。额度耗尽等到下一 UTC 日。旧版操作失败文案仅在未处理事项中迁移到重试；真正的模型 uncertain 不受迁移影响。

工作台“筛选中”显示排队、运行和等待重试的事项。Responses 答案增量按事项显示，调用工具时显示只读查询飞书资料状态；不转发私有推理、工具参数或原始工具输出。进度只在内存和工作台快照中同步，不逐字落盘，也不增加事项版本。关闭或范围变更会中止模型请求和当前聊天查询。页面有待筛选项时每秒刷新，重试显示原因和预计时间。

筛选依据个人职责和未闭环影响。`attentionProfile` 是用户授权后从历史整理的背景；该背景与具体系统故障可共同构成关联证据。核实影响、确认排查安排、跟进复发风险都属于动作，不限于本人亲自修复；没有 @、任务属于其他使用者、已有同事排查不能单独否定关联。对有关联的故障，quiet 需要恢复、取消或明确交接且无需本人继续关注的证据；调参、建议重试、观察和对 bot 的 `/stop` 不表示业务问题已解决。bot 报告中的归因仍须标明为待核实信息。群成员身份、领域词汇、@全体、严重标签本身不能推定本人负责；无个人关联的机器告警、一般讨论、成功通知仍 quiet。uncertain 仅用于已有明确关联、回查后仍缺少必要事实的事项；工具查询失败则自动重试。

工作台默认“待处理”合并展示未处理的 needed、uncertain 和旧版缺少 attention 的事项，具体证据或待确认信息保留在事项说明中；草稿生成并不等于已处理。pending 单列在“筛选中”，quiet 可在全部事项查看。标记已处理独立于分析状态。忽略（含批量忽略）是用户明确排除：attention=quiet，停止当前事项的筛选/重试/深入分析，仅在全部中作为无需动作保留，不计入已处理列表和数量。旧忽略记录启动时归一；用户主动恢复后才重新筛选。

## 通知节制

新版的事项话题替代关注摘要：每项开始分析时发一次通知，完成后在同话题回复草稿和分析结果；失败也在已建立的话题中说明。结果使用原生富文本消息，分别展示回复草稿、分析结果和待确认信息，保留正文的 Markdown 格式；发送时不自动下载模型正文中的图片。不会额外发送关注摘要或逐条发送模型进度。没有话题通知适配器的旧集成继续使用原有摘要机制，不启动自动处理。

开始通知和结果投递前保存 outbox；开始通知的正文和幂等键也持久化。每阶段最多尝试 3 次，重试窗口 4 分钟；重试前重新核对处理状态、归属和接收范围。话题创建未确认时不启动 agent，结果投递失败不重新运行 agent。结果不确定时保留工作台事项并停止重复投递。发送只用机器人身份到已验证的配置目标，并校验每项回复锚点属于该群和话题，不发送原会话，不生成结构化 @。

## 设置

支持超时配置的版本提供 `analysisTimeoutMinutes`：每项飞书待办深入分析的总时限，默认 30 分钟，可设为 1–1440 的整数，包含模型运行、工具执行和重试等待，不包含分析队列中的等待。工作台“高级设置”可调整；使用统一配置时位于 `monitors.toml` 的 `[sources.lark]`，旧 JSON 配置位于 `inbox`。仅修改该项不会中断当前分析，后续启动的分析使用新值，已运行任务保留原截止时间；手动改文件由每 15 秒的配置检查读取。筛选仍有独立的 10 分钟上限，GitLab CI 和存储监控的分析时限不受此项影响。旧二进制会拒绝新的 TOML 字段，须先升级再配置。

加载支持每秒轮询的版本后，消息采集默认及最短间隔均为 1 秒，`pollSeconds` 可设为 1–3600，调度也每秒触发。已有配置中的间隔会保留，需改为 1 秒并保存；无控制台的 `run --profile` 实例需重启才会读取修改。此前版本的下限为 5 秒或 30 秒，需加载新版才支持 1 秒。

加载独立历史刷新版本后，新消息采集与会话历史刷新分别最多运行一轮，慢历史查询不会挡住下一轮新消息采集和筛选调度，也不会积压多轮历史请求。新消息搜索与分页耗时较长时，实际采集间隔仍会超过配置值；1 秒是最短调度间隔，不保证 1 秒内收到消息。采集和历史刷新各自失败后至少等待 60 秒再重试，历史刷新失败不会暂停正常采集。采集间隔不包含飞书搜索索引延迟、模型与工具查询和工作台同步耗时。旧运行实例仍需重启才能使用独立历史刷新。

加载即时筛选版本后，新事项在采集完成的同轮调度中即可筛选，不再等待静默 60 秒或创建满 120 秒。逐事项筛选版本按独立的筛选并发上限调度。同一会话/话题按既有规则合并为一个事项，正在筛选时收到多条消息只更新该事项的待筛内容，不按消息数追加任务。基于旧消息版本的筛选结果不会触发分析或覆盖最新消息。独立历史刷新版本在当前事项筛选结束后立即唤醒调度，用合并后的最新上下文补筛；筛选通过的事项也可直接竞争分析槽，不必再等下一轮采集。同一事项分析互斥、独立并发池及失败退避仍生效。同一消息的重复拉取不会再次筛选。内容在补筛期间再次变化仍需继续补筛，因此持续讨论不能保证只调用一次模型。

加载增量分析版本后，已入队但尚未开始的分析遇到新内容仍会先重新筛选；运行中的分析继续完成，普通新消息和消息编辑合并入库，不取消或启动并行的同事项分析。模型启动前的消息纳入本轮输入；启动后新增或修改的内容在本轮完成后统一补筛。旧运行实例仍需重启才能使用此策略。

补筛同时提供已有结论、证据及全部已保留的增量消息，明确区分：无关消息或无实质变化时保留原关注状态及草稿，不重跑；有实质变化时复用已有调查产物进行补充分析；原问题确认解决时不再投递过时草稿。必要查询失败保持退避重试，事实不足保留待核对。补筛期间又来新消息时丢弃过期筛选判断，用最新合并内容继续筛选。每个事项独立携带自身增量；上下文超过查询限制时保留待重试状态，不截掉增量消息后作判断。

当前分析结果和已核对消息指纹一起持久化；有未核对增量时，工作台保留结果并标记草稿需核对，待补筛通过后再投递。已投递且无需更新的结果不重复发送。重启保留待补筛消息；被中断、手动停止或人工编辑的分析不会因新消息自动恢复，必须明确要求重新处理。同一事项的自动补筛复用已有的开始通知、发送去重标识和话题，不因每条新消息重新通知；用户手动要求重新分析时仍可发送新的开始通知。筛选和通知失败的重试退避继续生效，新消息不会绕过退避。手动忽略、接手和编辑草稿的保护保持；这些行为不缩短下述历史上下文窗口。

缩短间隔不缩短上下文：采集仍从各自游标向前重叠 5 分钟，完成分页后才推进该来源游标；未完成或失败的分页不推进。深入分析仍按 `contextMinutes` 向事项首条消息前回查（默认 15 分钟），合并后按 `maxContextChars`（默认 24,000 字符）和最多 100 条消息保留最近内容。这些是既有边界；迟到超过重叠窗口或内容超过上限的情况不能保证全部保留。

初始窗口不限制分析时的主动检索。关注筛选的 `search_messages` 支持关键词、会话 ID、时间范围和分页，另有 `read_chat_messages`、`read_thread_messages` 和 `get_messages`；这些工具直接使用当前执行 profile 的用户授权查询飞书。深入分析使用完整 agent 的终端工具调用同一 profile 的 `lark-cli --as user`，可调整关键词、扩大时间范围、读取话题或按消息 ID 补查。上下文不足时应先检索再判断，查询失败须保留为缺失证据，不能当作空结果。

根配置的 `inbox` 包含：

```json
{
  "enabled": false,
  "executorProfile": "codex",
  "ownerOpenId": "ou_OWNER",
  "destination": { "chatId": "oc_RESULT", "threadId": "omt_TOPIC", "replyTo": "om_ANCHOR" },
  "deliveryMode": "thread",
  "intakeScope": "private_mentions",
  "attentionProfile": "用户授权整理的具体工作背景",
  "dailyTriageLimit": 1000000,
  "analysisTimeoutMinutes": 30,
  "pollSeconds": 1,
  "contextMinutes": 15,
  "maxContextChars": 24000,
  "gui": { "publicUrl": "https://your-app.example/app/app_ID", "apiKeyFile": "/absolute/private/key" }
}
```

接收范围：`private` 私聊；`private_mentions` 私聊和直接 @ 本人的群消息（含相关回复）；`all` 所有可读取的私聊和群消息。与开关独立，关闭时可保存；范围变更从新消息开始，不补入旧会话，保留已有事项。本人回复、结构化报警恢复、结束语、结果群消息仍按既有规则处理。

旧 `autoAnalyze/waitMinutes/dailyAutoLimit` 字段只为快照兼容保留，`autoAnalyze` 始终归一为 false，旧 countdown 和未确认的自动队列不执行。新的自动处理由 `needed` 筛选结果触发，不受已废弃的 countdown 额度控制。旧 mode=manual/auto 命令拒绝。`attentionControl=true` 表示支持关注筛选；本文的新话题处理流程在运行实例加载新版 Bridge 后才生效，旧实例仍需手动深入分析。

所需用户读取能力包含 `search:message`、`im:chat:read`、`im:message.p2p_msg:get_as_user`、`im:message.group_msg:get_as_user`。CLI 保持 profile 的 bridge-bound 身份，身份失效暂停，不换账号。仅群授权时不启动 OAuth，授权须在私聊完成。

## 保存与批量操作

`deliveryMode=new_topic` 将每个需要关注的事项单独发到配置的话题群，包含原消息和工作台入口；批内部分发送失败时，各事项保持独立幂等键重试。关注筛选将用户授权的重点协作群、近期实质参与、小群具体请求和同议题追问作为关联线索，必要时先查前文；群小或活跃本身不自动产生待办，普通闲聊和无个人关联的机器告警仍过滤。

本地权威状态为配置目录下 `inbox/state.json`，权限 0600，原子写入；包含消息、筛选结果、草稿、版本、已处理状态、额度和通知 outbox。妙搭 PostgreSQL 保存工作台快照和 owner-scoped 指令；浏览器不是持久化来源。当前在采集周期清理 7 天前已处理事项，并限制无需动作的旧记录，不提供永久归档。

`review` 支持草稿保存和处理状态；`batch` 支持最多 500 项已处理或忽略。批量传 `{items:[{id,revision}],handlingState:"handled"|"ignored"}`，所有归属与版本均匹配后一次保存，任何冲突都不修改，落盘失败恢复内存状态；命令 ID 支持重试去重。关闭时可操作，不调用模型。运行中分析被取消，晚到结果不能覆盖人工操作。

工作台最多同步 500 项，优先需要关注和待核对；详情按 700 KB 快照预算预同步，其余按需读取。`@Type(() => Object)` 保留 jobs 为对象，兼容平台隐式转换。控制连接不依赖飞书聊天查询。

## 验证

针对性测试覆盖固定 Flash 路由、先建话题后启动、同话题草稿回复、通知与结果的幂等重试、重启恢复、筛选失败和预算、关闭/新消息/人工接手竞争、权限和目标验证、批量版本冲突及落盘失败。模型和飞书写入使用模拟接口验证，不能代替真实消息的筛选质量或上线验收。

## 操作延迟

支持 `compactSync` 的云端连接每秒领取指令；旧云端仍按 5 秒同步。快照没有变化时只上传连接身份，每 15 秒强制发送一次完整快照；云端空轮询最多每 10 秒更新心跳，避免每次都重写大 JSON。修改状态的快照随回执在同一事务中保存，重复回执不能覆盖新快照。浏览器提交后前 5 秒每 250 毫秒检查回执，之后每秒检查。

飞书消息采集在状态锁外运行，只在应用结果时短暂串行；范围和开关使用递增版本丢弃旧读取结果。批量处理无需等待后台消息接口返回。未变化的本地状态不重复 fsync。

JSON 仍是本地权威状态。迁移数据库应独立评估历史留存、索引和数据增长；当前这次优化没有迁移存储或改变已处理记录的归属。


## Claude 执行器配置

本地控制台可以选择个人 Claude profile 作为执行器，筛选服务另选已配置
Responses API 模型服务（无需 Codex profile）。下面是现有助理配置中的相关字段示例；
所属用户、目标话题等其余配置继续保留：

```json
{
  "executorProfile": "claude",
  "analysisModel": "",
  "triageService": "screening",
  "triageModel": ""
}
```

需要 Claude Code 2.1.302 或更新版本。`analysisModel` 也可填写 Claude 可用的
模型名称。首次开启前运行“检查配置”，分别核对执行器、飞书用户授权、筛选
服务和深入分析模型；配置检查不发送模型请求。当前模型服务拒绝请求或额度
不足时仍会产生安全的失败记录，不会将失败回复当成草稿。
